## Packaging (`packages/image-pipeline/src/drm.ts`, `runDrmJob`)

1. **The picture** (B1): sharp decodes the photo's `proof.webp` (the watermarked 1600 px proof parents already get; same
   pixels as the fallback, so D60's watermark stays) to raw sRGB, resized only to fit H.264 High level 4.0: even sides,
   at most 8,192 macroblocks, each side at most 4,096 px, never enlarged (`drmClipSize` in core). A 1600×1067 proof
   becomes 1600×1066; a 1600×1600 one 1432×1432. Codec `avc1.640028`.
2. **ffmpeg** (libx264) reads the frame 10 times from stdin: 2 seconds at 5 fps, one IDR then 9 P frames (`-g 10 -bf 0`,
   no scene cuts), BT.709 limited range and tagged as such, no metadata.
3. **Shaka Packager 3.9.3**: cbcs, raw key with `iv` = the key ID's bytes, `--clear_lead 0`, Widevine + PlayReady +
   FairPlay, `skd://<key ID>`, one on-demand file `drm.mp4` with a static `drm.mpd` and HLS `drm.m3u8` (master) and
   `drm-video.m3u8` (media, byte ranges).
4. Both binaries are checked against pinned SHA-256s before first use per cold start, run with an environment holding
   `PATH` only, without a shell; their error output is scrubbed of the key (hex any case, GUID dashes, base64,
   base64url) before it goes anywhere. The clear clip exists only in a private temp folder between the two tools and is
   removed in every case. The plaintext key is zeroed after packaging; it is never logged, stored or reported.
5. **Results.** The four files are stored (clip first, manifests last) with `Cache-Control: private, max-age=3600`, then
   the worker posts `{attempt, keyId, wrappedKey, kmsKeyArn, width, height, bytes}` to
   `POST /api/v1/internal/photo-worker/photos/{id}/drm` (signed, 4 KB). A missing proof, an unreadable one or one over
   20 MB is reported failed for good (`proof_missing`, `unreadable`, `too_large`); anything else (KMS, a tool, S3, the
   API) throws, so SQS retries.

**Binaries: the Lambda layer** (`apps/image-worker/layer/build-layer.mjs`). Lambda gets ffmpeg and the packager from a
layer at `/opt/bin`. The build downloads FFmpeg **7.0.2** static GPL for linux-arm64 with libx264 (John Van Sickle's
build as published in release **`b6.1.1`** of eugeneware/ffmpeg-static, last modified Nov 14, 2025), checking the `.gz`
and the binary against pinned SHA-256s, plus its GPL licence and build notes (also pinned); copies Shaka Packager's
arm64 binary from the pinned npm package (the spike's hash); writes the zip with fixed times, modes and order
(the zip's own hash isn't pinned: it depends on the zip tool's version; every file in it is); and fails on any mismatch or if the layer and function
would pass Lambda's 250 MB unzipped (it is about 61 MB). The deploy workflow publishes and attaches it when its new
input is ticked (Seenu approves the `staging` environment). The pins live twice, in the layer script and in the
pipeline (`DRM_BINARY_SHA256`), and a test keeps them equal.

**CI** (`.github/workflows/drm-packaging.yml`): runs only when packaging can change (the pipeline, the worker, core's
`drm.ts`, the lockfile), to save Actions minutes. It builds the arm64 layer from its pins, fetches the x64 builds of the
same versions, packages a synthetic picture with a throwaway random key and checks: it decrypts with the key to the
picture (PSNR > 35 dB), without the key to nothing usable (< 20 dB, or undecodable), and the key is in no output file in
any form. Checked here with the same binaries: decrypted PSNR was infinite (identical to the clear clip).

## Keys and KMS (B2, B4)

- One content key per photo: group photos and photos shown in several groups make per-child or per-group keys
  impossible. Key IDs are random v4 GUIDs; one Axinom license per large view opened.
- The worker asks the KMS key `daybell-{env}-ca-drm` (ca-central-1; its key ARN in the settings, never the alias) for a 16-byte data key with the encryption context
  `{studio, photo, key}` and sends only the wrapped copy. The worker's role may `GenerateDataKey` only with exactly those
  context keys, and never `Decrypt`.
- The token route unwraps with `Decrypt` and the same context, through a new Vercel OIDC role (`AWS_DRM_ROLE_ARN`) whose
  only right is that `Decrypt` (with a context condition). It must differ from `AWS_ROLE_ARN` and
  `AWS_DOWNLOAD_ROLE_ARN` (refused otherwise). The plaintext lives in memory until the token is signed, then is zeroed.
- `app.photo_drm_keys` keeps the wrapped key (only `ca-central-1` key ARNs accepted), cascading with its photo: a purge
  deletes it; a new round of processing or packaging replaces it.

## Entitlement and tokens

`shop_drm_key` (and `shop_drm_photo` for manifests) checks, in this order: a live session (`401
shop_session_required`) holding the child (else not found) → the child's shop open → the photo in
`app.parent_visible_photos(job, child, true)` (their portraits and their groups' photos, exactly the gallery) → a
Canadian studio (`region_unavailable`) → the switch on and the clip ready (`409 shop.drmUnavailable`). Anything a
parent may not see is **404**, exactly like a missing photo: another studio's, another session's, a sibling not in the
session, another group's, binned, flagged, card, unprocessed or a closed shop's photo. Over the budget: `429` with
`Retry-After` (to the end of the minute or the UTC day), nothing counted.

Routes (Node, `preferredRegion = "yul1"`, `callShopFunction` with its region check, `assertStorageRegion` before S3,
counted against **their own** network budget before anything else (300 a minute per network, 3,000 per /24 or /48;
review: tester #4), `?gallery=`, never cached):

- `GET /api/v1/shop/drm` → `{enabled, licenseUrls|null, fairplayCertificateUrl|null, codec}`.
- `GET /api/v1/shop/drm/fairplay-certificate` → the DER bytes (C10).
- `GET /api/v1/shop/children/{childId}/photos/{photoId}/drm-manifest?format=dash|hls|hls-media` → the stored manifest
  with `drm.mp4` replaced by a 600-second signed URL (`&` XML-escaped in the MPD); the HLS master's variant points back
  to this route with `format=hls-media` and the same gallery. Rewriting is strict: a manifest that isn't the packager's
  is refused.
- `POST /api/v1/shop/children/{childId}/photos/{photoId}/drm-token` → `{token, expiresAt}`: good from 5 s before to 60 s
  after; the communication key's ID, two dates and one inline key `{id, encrypted_key, iv, usage_policy}` under Policy A
  (Widevine `HW_SECURE_ALL`, PlayReady 3000, FairPlay HDCP type 1 with no AirPlay or AV adapter), `allow_persistence:
  false`. No name, code, studio, child or photo id. No `prevent_drm_message_reuse` or `jti` (C4).
- A malformed or missing setting turns DRM off (logged by variable name) rather than failing a parent's page.

## Viewer and fallback (C2, C7, C11)

- `DrmProvider` (in the shop layout) asks nothing until a large view opens. Then, once per gallery, `GET /shop/drm`;
  once per tab, `requestMediaKeySystemAccess` for the four hardware options only (Widevine `HW_SECURE_ALL`, PlayReady
  3000 in both forms, FairPlay), stored in `sessionStorage` as a plan (`dash`, `fairplay` or `none`) and a failure
  count: nothing personal. Shaka 5.2.12 is imported only when a plan exists.
- `DrmPhoto` (mounted once per open viewer): one Shaka player, `load()` per photo, destroyed on close. The video is
  muted, `playsinline`, `crossOrigin="anonymous"`, `disablePictureInPicture`, `disableRemotePlayback`, no controls,
  `aria-hidden`; the picture is a `role="img"` named with today's alt words. While loading, the photo's 400 px proof
  stands in and "Loading photo" appears after 500 ms (announced once per viewer, politely). No fade with reduced motion.
  Previous, Next, arrow keys and swiping are unchanged.
- **Fallback is silent** (C2): no protection for the photo, DRM off, no hardware DRM, an error, or nothing shown within
  **8 s** → the watermarked WebP as before. **Two failures in a row** → the WebP for the rest of the tab's session. A
  photo once shown under DRM never falls back. The gallery still signs `viewUrl` for every photo (C11): DRM deters; the
  WebP stays reachable by design.

## Blackout on computers (C1, C14)

`ProtectionProvider` reads the spike's Blackout signs through **one set of window listeners** for the whole shop: the
window losing focus, the page hidden, Shift with Cmd/Win or Ctrl held (and 1.5 s after), Print Screen, Cmd/Ctrl+P,
printing, the context menu. On a computer (`(hover: hover) and (pointer: fine)`) every `ProtectedImage` (grid, viewer
fallback, pose picker, bag, cover) becomes an ink panel with words (`aria-hidden`), its alt emptied, and one polite
status says "Photo hidden while a screenshot may be taken. It comes back in a moment." for the page; keyboard signs
empty the clipboard, best effort, **never** the window losing focus (C14). Phones and tablets keep round 7's blur exactly (review #6c)
and their clipboard is never touched. Amended by the review fixes: only pure modifier chords count, never in a field. The DRM video itself isn't blacked out by Blackout: hardware DRM does that.

## CSP, Permissions-Policy and CORS

- `media-src 'self' blob: <bucket>`; `connect-src 'self'` plus, only when `SHOP_DRM_LICENSE_PREFIX` is set and well
  formed, the bucket (Shaka fetches the clip's byte ranges) and exactly
  `https://<prefix>.drm-{widevine,playready,fairplay}-licensing.axprod.net`. No `'unsafe-eval'` and no `worker-src`:
  Shaka's only worker transmuxes MPEG-2 TS, which fMP4 clips never need (checked in its compiled build).
- `Permissions-Policy` gains `encrypted-media=(self)` on `/shop` and `/api/v1/shop`.
- S3 CORS gains the byte-range headers (`Range` allowed; `Content-Length`, `Content-Range`, `Accept-Ranges` exposed);
  `docs/aws-staging-photos.md` §14.7.

## Data (migration `20261018000000_shop_drm.sql`, forward only)

- `photos` gains `drm_status` (`requested | ready | failed`, null = never asked), `drm_key_id` (unique), `drm_attempt`
  (only grows: a late result of an earlier request is ignored), `drm_requested_at`, `drm_requests` (messages for the
  current request); not granted to browsers.
- `app.photo_drm_keys` and `app.shop_drm_rate`: `studio_id`, composite foreign keys with cascade, RLS on, no policies,
  nothing granted to anyone (the service role included); reachable only through the functions.
- Functions (SECURITY DEFINER, empty `search_path`, service role only, named errors without values):
  `photo_drm_requested`, `record_photo_drm_result`, `record_photo_drm_failed`, `photos_drm_due(limit)`,
  `shop_drm_photo`, `shop_drm_key`, `shop_drm_enabled()`, `set_shop_drm` (database owner only). Recreated:
  `photo_for_worker` (adds the request), `record_photo_result` (a new round drops the clip and key: reprocessing
  resets DRM, and the result route requests it again), `shop_gallery` (adds `drm` per photo), `prune_shop` (drops
  spent token counts).
- **Retries** (C8): SQS 5 receives, then the dead-letter queue (its alarm exists). The daily photos cron, where
  packaging is on, takes up to 2,000 photos: requests unanswered for an hour that were already queued 3 times become
  failed (a `drm_unavailable <photo id>` line); others are queued again; then photos never packaged (ready, not binned,
  not a card) are requested (the backfill). Locally (the local driver) nothing is packaged and the shop shows the WebP.

## Region (D113)

Photos, clips and keys stay in S3 and KMS in ca-central-1; packaging runs in the Canadian Lambda; tokens are signed and
keys unwrapped in Montréal (`yul1`). US studios: the database refuses (`region_unavailable`), `shop_gallery` marks
nothing protected, and the routes' storage guard refuses too. Queue messages carry `{photoId, make: "drm"}` only.
What reaches Axinom from the parent's browser: the license challenge, the parent's IP address (accepted in D158;
the privacy notice must say so, C9) and the token (no personal data).

## Risks

- **R1 — untested changes from the spike.** Real photos, one key per photo, P frames instead of all-intra, KMS keys and
  per-photo tokens haven't met a real device. The **device matrix on staging, switched on for Seenu's test studio only, is the gate** before the
  switch goes on anywhere parents are.
- **R2 — Safari autoplay after async steps.** `play()` now comes after a token fetch and a KMS unwrap, further from the
  parent's tap than on the spike's page; Safari may refuse a muted play it considers unprompted. Watch for the 8-second
  fallback on iPhone.
- **R3 — FairPlay production** needs Apple's production FPS certificate and Axinom's FairPlay setup; Safari keeps the
  WebP until `SHOP_DRM_FAIRPLAY_CERT` is set.
- **R4 — Axinom cost or outage.** One license per large view; an outage means 8 seconds then the WebP for every view
  (two failures then the tab stays on the WebP). The switch turns it off at once.
- **R5 — Lambda size and architecture.** The layer is about 61 MB of 250 MB; the arm64 binaries first run on Lambda.
- **R6 — Firefox.** Firefox has no hardware Widevine on most systems: the WebP under Blackout, by design.
- **R7 — PlayReady SL3000 with cbcs** needs PlayReady 4+; older hardware may refuse (then the WebP).
- **R8 — Axinom field names** (`iv`, `begin_date`, the policy fields) come from the research notes and the spike's
  device test, not from Axinom's documentation, which couldn't be reached from here.
- FairPlay HDCP type 1 (C12) may black out the photo on an external monitor or projector without HDCP 2.2.

## Rejected

- A key per child or per group (group photos and multi-group photos share one file).
- Packaging in the web app (Vercel functions' size and time limits; ffmpeg isn't there) or at upload in the preview
  step (a failure would hold up the previews).
- ffmpeg's own encryption (`cenc` only; FairPlay needs `cbcs`), and Axinom's key service (keys would leave our account).
- Downloading ffmpeg from johnvansickle.com directly: no tagged, permanent address for a given build could be found from
  here to pin; the b6.1.1 release carries the same build under a tag, pinned by hash.
- Keeping the token budget in memory (the spike's; separate Vercel instances count separately).
- Showing parents an error when DRM fails (C2: silent fallback).
- Removing `viewUrl` from the gallery (C11).
